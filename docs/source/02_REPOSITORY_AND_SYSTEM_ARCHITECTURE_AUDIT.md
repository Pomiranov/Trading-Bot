## Executive Summary

Проект — **не единая платформа, а три слабо связанных продукта в одном репозитории**: маркетинговый сайт (Next.js), операторский Dashboard (Flask + vanilla JS SPA), и торговое ядро с Telegram-ботом (Python). Качество каждого куска очень неоднородно.

**Главный архитектурный вывод:** система спроектирована и реализована как **однопользовательский (single-operator) торговый инструмент**, а сайт продаёт её как **многопользовательский SaaS с подписками**. Это не баг в коде — это отсутствующий слой архитектуры. В `bot/` нет ни таблицы клиентов, ни `tenant_id`, ни подписок, ни платежей: `grep -c` по `tenant|subscription|billing|stripe` даёт **0** совпадений на 187 файлов. Единственная сущность пользователя — `dashboard_users` (операторы с ролями), и единственный брокерский счёт — глобальный `TINKOFF_ACCOUNT_ID` из `.env`.

**Сильные стороны, которые надо сохранить:** слой `qf_platform` (репозитории/сервисы/контракты) и `/api/v2` — это профессиональная работа: единый envelope, коды ошибок, валидация всех query-параметров, guard-декораторы с CSRF/идемпотентностью/аудитом. Ноль `TODO`/`FIXME`/`HACK` на весь код. Внутренняя документация в коде (docstrings, объясняющие *почему*) — выше среднего отраслевого уровня.

**Главный технический долг:** дублирование Telegram-бота (два независимых приложения), legacy-слой `/api/v1` рядом с `/api/v2`, и разрыв между автономным торговым циклом `bot/main.py` и всей защитной инфраструктурой, построенной в `bot/ui/api/v2` (идемпотентность, аудит, подтверждения) — цикл её не использует.

### 3.1 Ключевой разрыв: защитная инфраструктура не покрывает торговый цикл (VERIFIED)

В `bot/ui/api/v2/routes_actions.py` реализован образцовый набор гарантий для мутирующих действий — декоратор `@mutating(action=..., idempotent=True, require_reason=True)` из `bot/security/guards.py:199` выполняет по порядку: read-only guard → CSRF → обязательная причина → идемпотентность (`action_idempotency`) → запись в `audit_events` с `state_before`/`state_after`.

**Этот механизм применён ровно к двум торговым действиям:** `POST /api/v2/positions/<id>/close` и `POST /api/v2/signals/<id>/execute`.

Автономный цикл в `bot/main.py:188` вызывает `tinkoff_client.place_market_order()` **напрямую**, минуя guards целиком: без идемпотентности, без записи в `audit_events`, без подтверждения. То же для Telegram: `bot/tg/handlers/trading.py:213` → `services/trading_service.execute_trade` → `gateway/trade_gateway`. Два из трёх путей исполнения сделки не защищены тем, что построено для третьего.

## 4. Findings

<a id="a-01"></a>
### [A-01] Отсутствует слой многопользовательности: система однопользовательская, а продаётся как SaaS

**Статус:** VERIFIED
**Критичность:** Critical
**Приоритет:** P0
**Компонент:** Архитектура целиком (bot/, website/)
**Доказательство:**
- `grep -rniE "tenant|subscription|billing|stripe" bot/ --include=*.py` → **0** совпадений (`tenant: 0`, `subscription: 0`, `billing: 0`, `stripe: 0`).
- Единственная таблица людей — `dashboard_users` (`bot/qf_platform/schema.py:450`), поля: `username`, `password_hash`, `role`, `trading_authorized`. Это операторы системы, не клиенты.
- Брокерский счёт один и глобальный: `TINKOFF_ACCOUNT_ID` (`bot/config.py:31`).
- Telegram-доступ — whitelist ID: `TELEGRAM_CHAT_ID` + `TELEGRAM_ALLOWED_IDS` (`bot/config.py:37-42`), проверка в `bot/tg/middlewares/auth.py:38`.
- Тикеры глобальные: `config.tickers` из `.env` (`bot/config.py:103`).
- Ни одна таблица данных (`trades`, `paper_accounts`, `equity_snapshots`, `trading_signals`) не содержит колонки владельца.
**Файлы и маршруты:** `bot/config.py`, `bot/qf_platform/schema.py:450-510`, `bot/tg/middlewares/auth.py`, `website/messages/ru.json` (`pricing.*`)
**Текущее поведение:** Один экземпляр системы обслуживает одного оператора с одним брокерским счётом. Сайт предлагает три тарифа (Sandbox бесплатно / Live 5 000 ₽ / Premium 10 000 ₽ в месяц) неограниченному числу посетителей.
**Ожидаемое поведение:** Либо (а) сайт позиционирует продукт как то, чем он является, либо (б) в архитектуру вводится клиентская сущность, изоляция данных по владельцу, хранение брокерских ключей per-user и привязка Telegram-аккаунта к клиенту.
**Влияние на пользователя:** При попытке обслужить второго клиента его сделки, позиции и equity попадут в те же таблицы без разделения; Telegram-бот ответит «Доступ запрещён» всем, кроме whitelist.
**Влияние на бизнес:** Монетизация, заявленная на сайте, технически неисполнима. Это первоочередной блокер публичного запуска.
**Техническое влияние:** Добавление multi-tenancy — самое дорогое изменение в проекте: затрагивает схему БД, все 18 репозиториев, все сервисы, аутентификацию, Telegram-привязку и хранение ключей.
**Корневая причина:** Продукт вырос из личного торгового бота; маркетинговый слой построен под будущую SaaS-модель, а ядро осталось однопользовательским.
**Рекомендация:** Принять решение по [OQ-ARCH-01](14_OPEN_QUESTIONS_AND_DECISIONS.md) до любой работы над подписками. Рекомендуемый путь для beta: оставить single-tenant, а «доступ» реализовать как ручной provisioning отдельного экземпляра на клиента (это соответствует уже заявленному на сайте «доступ выдаётся вручную, небольшими группами»).
**Зависимости:** Блокирует [P-01], [B-05], всю Phase 3 роадмапа.
**Оценка объёма:** XL
**Критерии приёмки:** Зафиксированное ADR с выбранной моделью (single-tenant-per-instance vs multi-tenant) и, при выборе multi-tenant, миграция схемы с `owner_id` на всех доменных таблицах + тесты изоляции.
**Roadmap ID:** RM-P0-001

<a id="a-02"></a>
### [A-02] Автономный торговый цикл исполняет реальные заявки без подтверждения человека

**Статус:** VERIFIED
**Критичность:** Critical
**Приоритет:** P0
**Компонент:** Торговое ядро (`bot/main.py`)
**Доказательство:**
- `bot/main.py:150-192`: при `sig.action == Action.BUY` цикл вызывает `orchestrator.check_signal()`, `risk_manager.check_trade_allowed()`, затем **сразу** `tinkoff_client.place_market_order(figi, quantity, direction="buy")`.
- `orch_decision["approved"]` (`bot/main.py:162`) — алгоритмическая проверка порога уверенности (`MIN_STRATEGY_CONFIDENCE = 0.20`, `bot/learning/trading_orchestrator.py:63`), **не** подтверждение человеком.
- `grep -niE "confirm|approve|pending|await_user|manual" bot/main.py` даёт единственное совпадение — строку 162 выше.
- Единственная реализация «подтвердить/отклонить на каждую сделку» — `bot/ui/telegram_bot.py` (`_pending_trades`, строки 43/202/605/711, обработчики зарегистрированы на 984-985). Этот модуль `main.py` не импортирует; его единственный потребитель — `bot/run_forward_d1.py:431`, и только для `send_notification`.
- Режим «advice-only» отсутствует: `grep -rniE "advice.?only|advisory|signal.?only"` по `bot/` → совпадений нет.
**Файлы и маршруты:** `bot/main.py:140-265`, `bot/ui/telegram_bot.py:165-230`, `bot/learning/trading_orchestrator.py:63`
**Текущее поведение:** При `TINKOFF_SANDBOX=false` цикл открывает и закрывает реальные позиции полностью автономно, каждые `POLL_INTERVAL` секунд по всем `config.tickers`.
**Ожидаемое поведение:** Для финансового продукта на этапе beta исполнение должно требовать явного подтверждения оператора, либо система должна иметь явный режим (`advice-only` / `manual-confirm` / `auto`) с безопасным значением по умолчанию.
**Влияние на пользователя:** Сайт обещает «последнее слово остаётся за вами» (`hero.subline`) и «Каждую сделку можно подтверждать вручную» (`audience.card1Body`). В автономном режиме это не так — подтверждение существует только для заявок, которые пользователь инициировал сам.
**Влияние на бизнес:** Расхождение публичного обещания и поведения кода на финансовом продукте — репутационный и потенциально юридический риск (см. [S-08](07_SECURITY_PRIVACY_AND_COMPLIANCE_AUDIT.md)).
**Техническое влияние:** Защитный контур (идемпотентность, аудит) обходится; сделка автономного цикла не попадает в `audit_events`.
**Корневая причина:** Функциональность подтверждения осталась в legacy-боте при переходе на `bot/tg/`; замена не была перенесена.
**Рекомендация:** Ввести обязательный режим исполнения в конфиге (`EXECUTION_MODE=advice|confirm|auto`) с `confirm` по умолчанию; перенести `_pending_trades`-логику из legacy-бота в `bot/tg/` и провести все три пути исполнения через `trade_gateway` с идемпотентностью и аудитом.
**Зависимости:** [T-01], [T-02], [A-05]
**Оценка объёма:** L
**Критерии приёмки:** При `EXECUTION_MODE=confirm` ни одна заявка не уходит брокеру без callback-подтверждения; тест воспроизводит блокировку; каждая исполненная заявка имеет строку в `audit_events`.
**Roadmap ID:** RM-P0-002

### [A-03] Нет автоматического аварийного отключения торговли (kill switch)

**Статус:** VERIFIED
**Критичность:** High
**Приоритет:** P1
**Компонент:** Risk management, торговое ядро
**Доказательство:**
- `grep -rnE "\.stop\(\)|stop_event\.set|halt|kill_switch" bot/risk/*.py bot/services/bot_engine.py` → единственное совпадение `bot/services/bot_engine.py:100` (`self._stop_event.set()`), вызывается только из операторских действий (`/api/v2/engine/stop`, Telegram `cb_bot_stop`) и обработчика сигнала ОС (`bot/main.py:_handle_signal`).

### [A-04] Торговое окно использует наивное локальное время, а лог утверждает UTC

**Статус:** VERIFIED
**Критичность:** High
**Приоритет:** P1
**Компонент:** Торговый цикл
**Доказательство:**
- `bot/main.py:119`: `now = datetime.now()` — наивное **локальное** время (без tz).
- `bot/main.py:120`: `if not (7 <= now.hour < 16):` — окно 07:00–16:00.
- `bot/main.py:121`: лог `"Exchange closed (%s UTC), waiting…"` — заявляет UTC.
- Для сравнения, весь остальной код торговых записей корректно использует `datetime.now(timezone.utc)` (`bot/main.py:226`, `:300`).
**Файлы и маршруты:** `bot/main.py:119-123`
**Текущее поведение:** Окно интерпретируется в таймзоне хоста. На сервере в MSK (UTC+3) окно 07–16 локального = 04:00–13:00 UTC, тогда как основная сессия MOEX — 06:50–15:40 UTC (09:50–18:40 MSK). Часть сессии не покрывается, часть сканирований идёт до открытия.
**Ожидаемое поведение:** Явная таймзона биржи (`Europe/Moscow`) и окно, привязанное к расписанию MOEX; учёт выходных и праздников.
**Влияние на пользователя:** Пропущенные сигналы в конце сессии; попытки торговать в закрытый рынок (заявки отклоняются брокером).
**Влияние на бизнес:** Стратегия исполняется не в том окне, на котором тестировалась — искажает всю статистику `belief_system`.
**Техническое влияние:** Расхождение лога и поведения затрудняет диагностику.
**Корневая причина:** `datetime.now()` вместо `datetime.now(ZoneInfo("Europe/Moscow"))`; комментарий не обновлён.
**Рекомендация:** Перейти на `zoneinfo`, вынести расписание в конфиг, добавить проверку торгового дня. Календарь праздников MOEX — отдельная задача.
**Зависимости:** —
**Оценка объёма:** S
**Критерии приёмки:** Юнит-тест с подменой таймзоны хоста подтверждает одинаковое окно; лог печатает фактическую таймзону.
**Roadmap ID:** RM-P1-006

<a id="a-07"></a>
### [A-07] Сильные стороны архитектуры (для сохранения при рефакторинге)

**Статус:** VERIFIED
**Критичность:** — (положительное наблюдение)
**Компонент:** `bot/qf_platform`, `bot/ui/api/v2`, `bot/security`

Эти решения следует считать эталоном проекта и не ломать:

1. **Контрактный слой `/api/v2`** (`bot/ui/api/v2/__init__.py`). Правило «роут парсит параметры, вызывает один сервис, оборачивает в envelope; ни SQL, ни арифметики» соблюдено. Все query-параметры валидируются с явными ошибками (`arg_environment`, `arg_ticker`, `arg_sort`, `arg_limit`) — неизвестное значение даёт `VALIDATION_FAILED`, а не тихий fallback. Обоснование прямо в коде: «тихо ответить на другой вопрос — это как live-число попадает на sandbox-экран».
2. **Разделение кодов отказа** (`bot/ui/api/v2/__init__.py:engine_or_fail`): `DB_UNAVAILABLE` ≠ `SCHEMA_OUT_OF_DATE`. Устраняет класс баг-репортов «четыре панели вечно грузятся».
3. **Миграции выведены из импорта** (`bot/qf_platform/migrate.py`). Раньше импорт `dashboard.py` выполнял ~40 `ALTER TABLE` в одной транзакции с тихим откатом. Теперь — отдельная команда, транзакция на statement, `--check` безопасен для прода.
4. **Guard-декоратор `@mutating`** (`bot/security/guards.py:199`) с фиксированным порядком проверок и явным замечанием, что read-only-отказ не должен «съедать» ключ идемпотентности.
5. **Режим `QF_DASHBOARD_READ_ONLY=1`** — проверен в работе: при запуске логирует точный перечень того, что стало неизменяемым. Позволяет проводить QA против реальных данных.
6. **Реконсиляция позиций с брокером** (`bot/main.py:_reconcile_positions_with_broker`) с честным docstring, объясняющим failure mode: `place_market_order` глотает исключения и возвращает `None`, включая таймаут *после* фактического исполнения.
7. **Ноль `TODO`/`FIXME`/`HACK`/`XXX`** на 187 Python- и 71 TS-файл.
8. **`build:messages` намеренно сломан** с объяснением — предохранитель против регрессии i18n.

4. Исправить таймзону торгового окна (RM-P1-006).
5. Устранить противоречия документации (RM-P0-004, RM-P0-005).
