## Механизм утечки: `git add` пишет блоб, скан ловит только КОММИТ

| | недостижимый блоб `003652e2` | отслеживаемая копия `measurements/2026-08-02_blockA/forward_d1.log` |
|---|---|---|
| строк | **1259** | **1259** — то же |
| байт | 110 935 | 112 164 |
| вхождений токена | **2** | **0** |
| строк `httpx: HTTP Request` | 2 | — |
| диапазон дат внутри | 2026-07-12 18:31:12 … 2026-08-02 00:15:10 | тот же файл |

Одинаковое число строк при разном размере и разном числе вхождений — подпись
редактирования: пометка вырезания длиннее вырезанного значения, поэтому чистая
копия **больше** грязной.

Восстановленная последовательность: копию лога положили в `measurements/`,
сделали `git add`, скан перед коммитом нашёл секрет, файл отредактировали, в
коммит ушла чистая версия. **Блоб грязной версии остался в `.git/objects`, потому
что его записал сам `git add`.**

⇒ **Скан перед коммитом предотвращает КОММИТ, а не ЗАПИСЬ.** Фраза «только скан не
дал ей уйти в коммит» была верна дословно и ложна по смыслу.

**На `origin` не уезжало** — замерено: недостижимых **коммитов** в базе нет (5
блобов, 2 дерева), значит блоб никогда не входил в коммит, а `git push` передаёт
только объекты, достижимые из отправляемых ссылок.

**Остальные шесть недостижимых объектов проверены оба значения** — чисто:

## Почему это оправдывает предикат целиком

Эту утечку **не нашла бы ни одна из трёх исходных форм**, и дело не только в
поломке `--`: объект недостижим ни из `--all`, ни из `--all --reflog` (2218 =
2218). Даже правильно написанная «третья форма», введённая именно ради
недостижимых объектов, дала бы **ноль** — и этот ноль прочитался бы как чистый
репозиторий.

## Хвост 3: чем мерились тесты. 268 против 230 — ДВЕ разницы, не одна

Число без пометки происхождения читается как измеренное, поэтому вот замер.

**268** получено командой `.venv/Scripts/python.exe -m pytest tests/ -q` из
`D:/Trading-Bot-Nik`. Подтверждено независимой формой — статический счёт
`grep -c 'def test_'` по `tests/` даёт **268**, то же число.

Разбивка (замерена `pytest <подкаталог> --collect-only -q`):

| область | главное дерево `merge-learning-nik` | дерево `worktree-notify-p2p1` |
|---|---|---|
| `tests/forward_tests/` | 210 | **230** |
| `tests/platform_tests/` | 39 | 39 |
| `tests/security_tests/` | 19 | 19 |
| **`tests/` всего** | **268** | **288** |

**Откуда «230 из 230» в хендоффе:** это `tests/forward_tests/` **в дереве
`worktree-notify-p2p1`** — 230 ровно. Согласуется с «20 новых»: 210 в главном
дереве плюс 20 несмерженных.

**Откуда «251 тест зелёный» (§2ж, 31.07):** статический счёт `def test_` на
коммите `1eddc79` (мерж 31.07) даёт **251** — то же число. По коммитам:

```
ed10e01 (30.07)  220
1eddc79 (31.07)  251   ← число из §2ж
2c1d506 (03.08)  288   ← коммит хендоффа, он на ветке worktree-notify-p2p1
HEAD             268
```

**Арифметика разницы, вся замерена:**

```
268 − 39 (platform_tests) − 19 (security_tests) + 20 (P2+P1, не смержены) = 230
```

То есть 268 и 230 расходятся по **двум** независимым причинам: **разная область**
(`tests/` против `tests/forward_tests/`) и **разное дерево** (`merge-learning-nik`
против `worktree-notify-p2p1`). Немонотонность 251 → 230 объясняется вторым:
хендофф мерил не то дерево, где стояло 251.

**+38 к моей правке отношения не имеет, и это проверено, а не заявлено:** коммит
`a4ae51c` не менял ни одного файла в `tests/` (0 файлов в диффе), статический счёт
`def test_` равен 268 и до него (`8fff410`), и после.
