# Quant — передача задач между агентами

> Общие правила — [`AGENTS.md`](../../../AGENTS.md). Форматы — [`TASK_SPECIFICATION.md`](../../../docs/agents/TASK_SPECIFICATION.md)
> и [`HANDOFF.md`](../../../docs/agents/HANDOFF.md) (17 полей). Политика постоянных чатов —
> [`PERMANENT_CHAT_POLICY.md`](../../../docs/agents/PERMANENT_CHAT_POLICY.md).

## Mission

Задача не теряется и не выполняется дважды. У каждой задачи в любой момент один владелец
и один исполнитель, и переход между ними явный.

## Trigger

Задача завершена; задача принадлежит другой роли; нужен исполнитель; пришёл чужой
результат; нужно решение владельца.

## Канонический цикл

```
Постоянный чат
  → анализирует
  → создаёт Task Specification
  → выбирает Agent Profile
  → создаёт task conversation
  → создаёт branch + worktree
  → выполняет задачу
  → возвращает handoff
  → создаёт Pull Request
  → Постоянный чат принимает результат
```

Постоянные чаты **не выполняют** работу, меняющую код. Они анализируют, ставят
и принимают. Исполнение живёт в отдельной task conversation со своим worktree.

## Кто что берёт

| Задача | Владелец постановки | Исполнитель |
|---|---|---|
| Приоритет, порядок, план, roadmap, backlog | 01 Control Center (PM) | — |
| Бизнес-требование, критерии приёмки, анализ данных | 01 Control Center (BA) | — |
| Реализация, рефакторинг, багфикс, миграция, безопасность, тесты, PR | 01 → | **02 Engineering** |
| Архитектурное решение, ADR | 01 → | **02 Engineering** |
| Дизайн экрана, состояния, токены, a11y, визуальная приёмка, Stitch | 01 или владелец | **03 UI/UX** |
| Позиционирование, воронка, SEO, metadata, OG, CRO, контент, тарифы | 01 или владелец | **04 Marketing** |
| Мандат на T0, merge в `main`, деньги, юридический текст, секреты | — | **владелец** |

Правило разрешения спора: если два чата считают задачу своей — решает 01 Control Center.
Если задача про то, **как выглядит** — 03. Про то, **как объясняется и продаётся** — 04.
Про то, **как работает** — 02.

## Что обязана содержать передача в Engineering

Минимум, без которого задачу нельзя начинать:

1. **Task ID** (например `RM-P0-003`; в ветке — в нижнем регистре).
2. Зона поражения T0–T4 и радиус.
3. Мандат владельца, если T0 или правка `AGENTS.md` / `CLAUDE.md`.
4. Ветка по правилам `AGENTS.md §3`: `agent/claude/<task-id>-<slug>`.
5. Файлы для чтения **перед** правкой и что в них искать.
6. Что можно менять / читать, но не менять / не трогать вообще — конкретными путями.
7. Definition of Done командами с ожидаемым выводом.
8. Раздел «Не делать».
9. Для T0/T1 — требование падающего теста до правки и раздел «Откат».
10. Требование отчёта: изменённые файлы, вывод каждого гейта, находки вне скоупа.

## Что обязан вернуть исполнитель

Handoff по 17 полям [`HANDOFF.md`](../../../docs/agents/HANDOFF.md).
Без полного handoff задача **не сдана** — независимо от того, работает ли код.

Обязательно в handoff: Task ID, ветка, базовый commit, свой commit, список изменённых
файлов, вывод каждого гейта с exit code, красные гейты, которые были красными до правки
(с их ID), находки вне скоупа, что осталось непроверенным, ссылка на Pull Request.

## Приёмка

Control Center принимает результат, проверяя:

- заявленные команды и их exit codes воспроизводимы;
- изменённые файлы соответствуют скоупу, лишнего нет;
- `git status` в worktree чист;
- все 17 полей handoff заполнены;
- находки вне скоупа не «исправлены заодно», а зафиксированы;
- ни один секрет не выведен и не закоммичен.

Вердикт: **принято** / **на доработку** (с конкретным списком) / **отклонено** (с причиной).

## OWNER CHECKPOINT

Оформляется, когда дальше нельзя без владельца. Формат:

```
OWNER CHECKPOINT — <одна строка, что именно нужно>
Блокирует: <что стоит без этого>
Почему нельзя решить самому: <причина>
Что сделать владельцу: <конкретные шаги или команда>
Что уже готово и ждёт: <состояние>
```

Секрет **никогда** не запрашивается значением в чат — только описанием, куда владелец
должен его вставить (`AGENTS.md §8`).

## Prohibited actions

- Не начинать задачу без Task ID и без ветки.
- Не накапливать несвязанные изменения в одном worktree.
- Не передавать задачу «в воздух»: у передачи всегда есть адресат из таблицы выше.
- Не принимать результат по словам — только по воспроизводимым командам.
- Не закрывать задачу без handoff.
- Не расширять скоуп при передаче: новая находка — новая задача с новым Task ID.
- Не запрашивать значение секрета в чат.
- Не мержить в `main` — merge выполняет владелец.

## Definition of Done

Передача считается выполненной, когда у принимающей стороны есть всё, чтобы начать
без единого уточняющего вопроса, и у передающей — запись о том, что и кому передано.
