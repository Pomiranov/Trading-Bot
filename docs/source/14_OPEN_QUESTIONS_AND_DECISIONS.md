## Как пользоваться документом

Здесь собраны вопросы, ответ на которые **не выводится из кода** — он требует решения владельца, внешней экспертизы или данных, которых пока нет. Для каждого: почему это важно, что зависит, варианты с рисками, рекомендация (если она обоснована), кто решает и крайний момент.

**«Крайний момент»** — не календарная дата, а событие в проекте, после которого решение станет дороже или невозможно.

Принятое решение оформляется как ADR в `docs/adr/` и здесь помечается как закрытое со ссылкой.

**Сводка:** 27 вопросов. Из них **6 блокируют планирование** и должны быть решены до начала Phase 1.

### OQ-PROD-01 · Что показывать в блоке тарифов до подключения оплаты?

## Architecture

### OQ-ARCH-01 · 🔴 Модель доступа: single-tenant per instance или multi-tenancy?

**Почему важно:** **Самый важный открытый вопрос проекта.** От него зависит объём почти всей дальнейшей работы. Система сейчас однопользовательская: 0 совпадений по `tenant|subscription|billing` на 187 Python-файлов; ни одна доменная таблица не имеет владельца; один брокерский счёт; whitelist `chat_id`.
**Зависит:** схема БД, все 18 репозиториев, аутентификация, хранение брокерских ключей, Telegram-привязка, биллинг, onboarding. Прямо блокирует RM-P1-023 (XL или ничего), RM-P3-026 и всю Phase 3.
**Варианты:**
| Вариант | Объём | Риск |
|---|---|---|
| **A. Single-tenant per instance** — отдельный экземпляр на клиента, ручной provisioning | XS (схема не меняется) | Не масштабируется дальше десятков; эксплуатация растёт линейно; каждый клиент — свой хост и свои секреты |
| **B. Multi-tenancy** — `owner_id` на всех доменных таблицах, изоляция, ключи per-user | XL | Самое дорогое изменение в проекте; риск ошибки изоляции данных = утечка финансовых данных между клиентами; требует переработки всех репозиториев и тестов изоляции |
| C. Гибрид: multi-tenant для чтения, отдельные процессы для торговли | L | Сложность двух моделей одновременно |
**Рекомендация:** **A для beta.** Три обоснования: (1) это **уже** то, что заявлено на сайте — «доступ выдаётся вручную, небольшими группами»; (2) стоит XS вместо XL и не требует миграции данных; (3) при 3–10 beta-пользователях ([OQ-BIZ-02]) масштабирование не является ограничением. Переход к B — осознанное решение после подтверждения спроса, и его правильно делать **до** накопления клиентских данных, а не после.
**Кто решает:** владелец продукта + Backend workstream. **Оформить ADR обязательно.**
**Крайний момент:** **до начала Phase 1.** Без этого решения оценки Phase 1–3 недостоверны, а любая работа над клиентским кабинетом ведётся по неизвестному ТЗ.
**Связь:** [A-01](02_REPOSITORY_AND_SYSTEM_ARCHITECTURE_AUDIT.md#a-01), [B-01](06_BACKEND_DATA_AND_INTEGRATIONS_AUDIT.md#b-01), [D-01](04_DASHBOARD_AUDIT.md#d-01), [T-04](05_TELEGRAM_BOT_AUDIT.md#t-04) · RM-P0-001

## Security

### OQ-SEC-01 · 🔴 CVE: принять риск или апгрейдить Next до 16?

**Почему важно:** `npm audit --omit=dev` → **3 high severity** (postcss: XSS + path traversal + произвольное чтение файлов; sharp: 4 CVE libvips). Фикс требует `next@16.3.0` — мажорный апгрейд с 15.5.22.
**Фактическая эксплуатируемость (важна для решения):** postcss — сборочная зависимость, векторы требуют недоверенного CSS или `sourceMappingURL`; весь CSS авторский. sharp используется `next/image`, но на сайте **0** элементов `<img>` и `next/image` не используется — runtime-путь не задействован. То есть риск в текущей конфигурации низкий, но CVE присутствуют в дереве и будут зафиксированы любой внешней проверкой.
**Варианты:**
| Вариант | Риск |
|---|---|
| A. Принять риск, зафиксировать в ADR с датой пересмотра | CVE останутся в отчётах; при изменении конфигурации (появление `next/image`) риск вырастет |
| B. Апгрейд Next 16 | Мажорный: Turbopack, App Router, совместимость `next-intl` 4.x; требует полного регресса сайта |
| C. `overrides` для postcss/sharp на пропатченные версии | Может сломать сборку; неподдерживаемая конфигурация |
**Рекомендация:** **A сейчас + C как попытка + B запланировать.** Мажорный апгрейд в обход регресса опаснее самих CVE в текущей конфигурации. **Не выполнять `npm audit fix --force`.**
**Кто решает:** Security + Frontend Architecture.
**Крайний момент:** до Release Gate Phase 1.
**Связь:** [S-03](07_SECURITY_PRIVACY_AND_COMPLIANCE_AUDIT.md#s-03) · RM-P1-017
