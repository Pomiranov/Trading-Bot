## Executive Summary

**Безопасность — сильнейшая инженерная сторона Python-части проекта.** Это не типичный уровень для проекта такого размера: серверные сессии вместо JWT (с объяснением, почему JWT отвергнут), полноценный CSP с per-request nonce, двухуровневая защита от подбора пароля, идемпотентность мутаций, audit trail с фиксацией переходов состояния, AES-256-GCM для секретов, и — что показательно — `Secure`-cookie **по умолчанию включены**, а отключаются только явным opt-out для localhost.

Проверка фактическая, а не по документации: **все** эндпоинты данных и действий Dashboard возвращают `401` без сессии; публичны ровно пять маршрутов, и каждый из них обоснован.

**Существенные технические пробелы:**

| Пробел | Где | Критичность |
|---|---|---|
| Нет полноценного CSP `script-src` на сайте (при том что в Dashboard он есть) | website | High |
| 3 high-severity CVE в транзитивных npm-зависимостях; фикс требует мажорного апгрейда Next | website | High |
| Секреты остаются в открытом `.env` без `SECRETS_MASTER_KEY` | bot | High |
| Идемпотентность и аудит не покрывают 2 из 3 путей исполнения сделки | bot | High |
| Нет production WSGI (Werkzeug dev-сервер) | dashboard | High |
| Нет бэкапа и процедуры восстановления | infra | High |
| Нет CI/CD → нет автоматической проверки безопасности | всё | High |
| Мёртвый auth-модуль (`dashboard_auth.py`) создаёт ложное впечатление механизма | bot | Medium |

**Юридический контур не закрыт вовсе** и это главный не-технический риск: privacy policy, пользовательское соглашение и страница раскрытия рисков **отсутствуют** (404), при том что сайт собирает email и подключает три аналитических сервиса. Дисклеймер в footer есть и сформулирован корректно, но одного дисклеймера недостаточно. **Требует юриста.**

## 1. Аутентификация и авторизация (VERIFIED)

### 1.1 Dashboard — серверные сессии

Реализация — `bot/security/session_auth.py`, таблицы `dashboard_users` / `dashboard_sessions` / `dashboard_login_attempts`.

Docstring файла фиксирует отвергнутую альтернативу: до этого была схема, где авторизация была «IP-based rather than cookie-based», и `SameSite` не давал защиты от CSRF. Схема в `schema.py:447` прямо помечает: «Server-side sessions. **No JWT**, no client-side claims, no default password».

| Механизм | Реализация | Оценка |
|---|---|---|
| Хранение пароля | Argon2id (`argon2-cffi`), с fallback на Werkzeug scrypt; **алгоритм записан внутрь дайджеста**, поэтому апгрейд — это re-hash при следующем входе | Отлично |
| Сессия | Непрозрачный `sid` в cookie; всё состояние на сервере | Отлично |
| Cookie сессии | `HttpOnly=True`, `SameSite=Strict`, `Secure` по умолчанию, `path=/` | Отлично |
| CSRF | Double-submit: отдельная cookie **намеренно не** `HttpOnly` (`session_auth.py:318-333`), с объяснением «бесполезна без HttpOnly сессионной cookie» | Отлично |
| `Secure` по умолчанию | `secure_cookies()` (`:58-67`): возвращает `True`, если `QF_HTTPS=1`, иначе `True` **если не задан** явный `QF_INSECURE_COOKIES=1`. То есть забытая конфигурация даёт **безопасное** поведение | Отлично — fail-safe |
| Роли | `dashboard_users.role` + `bot/security/permissions.py` (`Permission`), `trading_authorized` отдельным флагом | Хорошо |
| Принуждение | `@app.before_request` fail-closed; allow-list **путей**, а не IP | Отлично |

### 1.2 Защита от подбора — два независимых уровня (VERIFIED)

`bot/security/session_auth.py:48-55`, docstring: «bursts, and a persistent per-user lockout against a slow distributed guess».

| Уровень | Параметр | Значение по умолчанию |
|---|---|---|
| Burst-лимит (по username **или** IP в окне) | `QF_LOGIN_WINDOW_SECONDS` / `QF_LOGIN_MAX_FAILURES` | 300 с / 5 попыток |
| Постоянная блокировка аккаунта (подряд) | `QF_ACCOUNT_LOCK_AFTER` / `QF_ACCOUNT_LOCK_MINUTES` | 10 попыток / 15 минут |

Хранение — `dashboard_login_attempts` (`auth_repository.py:195,216,230`) + счётчики блокировки на `dashboard_users` (`:53`). Два уровня закрывают и быстрый флуд, и медленный распределённый подбор — это осознанная модель угроз, а не одна галочка.

### 1.3 Telegram — whitelist chat_id

Fail-closed (`bot/tg/middlewares/auth.py:44-49`): при пустом whitelist доступ **закрыт** и логируется ошибка конфигурации. Подробно — [05, T-04](05_TELEGRAM_BOT_AUDIT.md).

### 1.4 Website — аутентификации нет и не требуется

Публичный маркетинговый сайт; единственный вход — `POST /api/beta` (неаутентифицированный, с rate-limit и honeypot).

## 2. Findings

<a id="s-01"></a>
### [S-01] Отсутствуют privacy policy, пользовательское соглашение и страница раскрытия рисков

**Статус:** VERIFIED
**Критичность:** Critical
**Приоритет:** P0
**Компонент:** `website/`
**Доказательство:**
- HTTP-пробы: `/ru/privacy` → **404**, `/ru/terms` → **404**, `/ru/legal` → **404**. Маршрутов нет в `src/app/[locale]/`.
- В `sitemap.xml` только `/en` и `/ru`.
- При этом собираются персональные данные: форма запрашивает email (`accessForm.emailLabel` — «Рабочая почта»), а `accessForm.consentNote` заявляет «Отправляя форму, вы соглашаетесь на переписку об этом продукте» — то есть согласие **декларируется**, но документа, на который оно ссылается, не существует.
- Подключены три аналитических сервиса: PostHog, Vercel Analytics, Vercel Speed Insights (см. [W-08](03_WEBSITE_AUDIT.md)).
- Комментарий в коде `page.tsx` упоминает «before legal pages make this a multi-page site» — то есть юридические страницы **запланированы**, но не созданы.
- Что **есть**: дисклеймер в footer (`footer.legal`) — «Торговля сопряжена с риском потери капитала. Материалы на сайте не являются индивидуальной инвестиционной рекомендацией» — сформулирован корректно и уместно.
**Файлы и маршруты:** `/ru/privacy`, `/ru/terms`, `/ru/legal` (404); `website/src/components/sections/footer/footer.tsx`
**Текущее поведение:** Персональные данные собираются и передаются трекерам без публичного документа, описывающего цели, основания, сроки хранения и права субъекта.
**Ожидаемое поведение:** Публичные privacy policy и terms; для финансового продукта — отдельное раскрытие рисков, а не только строка в footer.
**Влияние на пользователя:** Невозможно узнать, что происходит с его данными.
**Влияние на бизнес:** Регуляторный риск при работе с аудиторией РФ (152-ФЗ) и, при трафике из ЕС, GDPR. **Конкретные требования, необходимость согласия и формулировки должен определить профильный юрист** — здесь фиксируется только факт отсутствия документов.
**Техническое влияние:** Инфраструктура готова: комментарий в `layout.tsx` подтверждает, что ассистент-орб намеренно вынесен на уровень layout, «чтобы он выжил на любом будущем маршруте под `[locale]`: точка входа, исчезающая на юридических страницах, была бы хуже её отсутствия». То есть добавление страниц предусмотрено архитектурно.
**Корневая причина:** Юридический контур не входил в скоуп редизайна.
**Рекомендация:** (1) Привлечь юриста — это не задача разработки. (2) Создать `/[locale]/privacy`, `/[locale]/terms`, `/[locale]/risk-disclosure` с i18n-паритетом (`check:i18n` проследит). (3) Связать из footer. (4) Решить модель согласия на трекинг по итогам заключения ([OQ-LEGAL-01](14_OPEN_QUESTIONS_AND_DECISIONS.md)).
**Зависимости:** [W-08], [B-05]
**Оценка объёма:** M (реализация) + внешняя юридическая работа
**Критерии приёмки:** Страницы опубликованы в обеих локалях, связаны из footer, перечисляют все фактические трекеры и приёмник заявок; заключение юриста зафиксировано.
**Roadmap ID:** RM-P1-011

<a id="s-02"></a>
### [S-02] На сайте нет полноценного CSP `script-src` — при том что в Dashboard он реализован

**Статус:** VERIFIED
**Критичность:** High
**Приоритет:** P1
**Компонент:** `website/next.config.ts`
**Доказательство:**
- Сайт отдаёт `Content-Security-Policy: frame-ancestors 'none'` — **только** эту директиву. Комментарий в `next.config.ts` это признаёт прямо и объясняет: полноценная политика требует per-request nonce из middleware, а этот файл сейчас занят `next-intl`; «неверный nonce — это белая страница», поэтому изменение отложено в отдельный проход. Зафиксировано в `website/docs/SECURITY_REVIEW.md`.
- **Dashboard эту же задачу решил:** живой заголовок содержит `script-src 'self' 'nonce-5o8dc0vg-bv7LpvDHycxXQ'` вместе с `default-src 'self'`, `object-src 'none'`, `base-uri 'none'`, `form-action 'self'` (`bot/security/http_middleware.py:_csp`).
- Что на сайте **есть** (проверено в `next.config.ts` и живом ответе): `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, обширный `Permissions-Policy` (включая `payment=()`), `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`, `Cross-Origin-Opener-Policy: same-origin`, `poweredByHeader: false`.
**Файлы и маршруты:** все страницы сайта; для сравнения — `bot/security/http_middleware.py:108-113`
**Текущее поведение:** XSS-вектор на сайте не ограничен политикой скриптов. Практический риск умеренный: страница статическая (SSG), пользовательского контента не рендерит, единственный ввод (email) не отображается обратно. Но защиты в глубину нет.
**Ожидаемое поведение:** `script-src` с nonce, как в Dashboard.
**Влияние на пользователя:** При появлении XSS (например, через будущую интеграцию или сторонний скрипт) ущерб не ограничен.
**Влияние на бизнес:** Для финансового бренда отсутствие CSP — типовое замечание при любой внешней проверке безопасности.
**Техническое влияние:** Нужна композиция middleware: `next-intl` + генерация nonce. Решение в проекте уже есть — паттерн из Dashboard переносим.
**Корневая причина:** Осознанно отложено с документированной причиной (не забыто).
**Рекомендация:** Реализовать nonce в `src/middleware.ts`, скомпоновав с `createMiddleware(routing)`. Обязательно проверить: страница рендерится, PostHog/Vercel Analytics работают, hydration без ошибок. Разворачивать через `Content-Security-Policy-Report-Only` до подтверждения, чтобы не получить белую страницу в production.
**Зависимости:** —
**Оценка объёма:** M
**Критерии приёмки:** Ответ содержит `script-src` с nonce; консоль без CSP-нарушений; аналитика функционирует; в `Report-Only` неделю без нарушений перед принудительным включением.
**Roadmap ID:** RM-P1-016

### [S-03] Три high-severity CVE в транзитивных npm-зависимостях; фикс требует мажорного апгрейда Next

**Статус:** VERIFIED
**Критичность:** High
**Приоритет:** P1
**Компонент:** `website/package-lock.json`
**Доказательство (`npm audit --omit=dev`, exit 1):**

| Пакет | Проблема | Путь |
|---|---|---|
| `postcss` | GHSA-qx2v-qp2m-jg93 (XSS через неэкранированный `</style>` в CSS stringify); GHSA-6g55-p6wh-862q и GHSA-r28c-9q8g-f849 и GHSA-fxqj-rqcc-2cmp (произвольное чтение файлов / path traversal через контролируемый атакующим `sourceMappingURL`) | `node_modules/next/node_modules/postcss` (транзитивно через `next`) |
| `sharp` | GHSA-f88m-g3jw-g9cj — унаследованные уязвимости libvips: CVE-2026-33327, CVE-2026-33328, CVE-2026-35590, CVE-2026-35591 | `node_modules/sharp` (транзитивно через `next`) |

Итог: **3 high severity vulnerabilities**. `npm audit fix --force` предлагает `next@16.3.0` — **breaking change** с текущей 15.5.22.

**Честная оценка фактической эксплуатируемости:**
- `postcss` — сборочная зависимость. Векторы требуют обработки **недоверенного CSS** или недоверенного `sourceMappingURL`. Весь CSS проекта авторский; пользовательский CSS не обрабатывается. Риск в runtime — низкий; риск в цепочке сборки — реальный, если сборка когда-либо получит недоверенный вход.
- `sharp` используется Next для оптимизации изображений. Проверено: на сайте **0** элементов `<img>`, вся графика — CSS/SVG (см. [W-06](03_WEBSITE_AUDIT.md)); `next/image` в `src/` не используется. То есть runtime-путь к `sharp` фактически не задействован.

Это **не** повод игнорировать: CVE присутствуют в дереве зависимостей, и любая внешняя проверка их зафиксирует.
**Файлы и маршруты:** `website/package.json`, `website/package-lock.json`
**Текущее поведение:** 3 high CVE в дереве production-зависимостей.
**Ожидаемое поведение:** Чистый `npm audit` либо документированное принятие риска с обоснованием.
**Влияние на пользователя:** В текущей конфигурации — практически отсутствует (см. оценку выше).
**Влияние на бизнес:** Замечание при любом security review; для финансового продукта — вопрос доверия.
**Техническое влияние:** Апгрейд до Next 16 — мажорный, требует регресса всего сайта (Turbopack, App Router, next-intl 4.x совместимость).
**Корневая причина:** Транзитивные зависимости фреймворка; апстрим-фикс доступен только в мажорной версии.
**Рекомендация:** **Не выполнять `npm audit fix --force` сейчас** — это ограничение аудита и одновременно правильное инженерное решение: мажорный апгрейд в обход регресса опаснее самих CVE. Вместо этого: (1) зафиксировать принятие риска с обоснованием выше; (2) запланировать апгрейд Next 16 отдельной задачей с полным регрессом; (3) до апгрейда — попробовать `overrides` в `package.json` для `postcss`/`sharp` на пропатченные версии и проверить, что сборка проходит.
**Зависимости:** [Q-01](08_QA_TESTING_PERFORMANCE_AND_RELIABILITY_AUDIT.md) — без CI это не отслеживается автоматически
**Оценка объёма:** S (overrides) / L (апгрейд Next 16)
**Критерии приёмки:** Либо `npm audit --omit=dev` чист, либо принятие риска зафиксировано в ADR с датой пересмотра; в CI появился шаг `npm audit`.
**Roadmap ID:** RM-P1-017

<a id="s-04"></a>
### [S-04] Секреты остаются в открытом `.env`, если не задан `SECRETS_MASTER_KEY`

**Статус:** VERIFIED
**Критичность:** High
**Приоритет:** P1
**Компонент:** `bot/security/encryption.py`, `credential_vault.py`
**Доказательство:**
- `SecretBox.from_env()` (`encryption.py:45-53`): при пустом `SECRETS_MASTER_KEY` возвращает **`None`** — шифрование просто выключено.
- `CredentialVault.try_create()` (`credential_vault.py:37`) без `SecretBox` не активируется; `enabled()` (`:47`) вернёт `False`.
- Следствие: `TINKOFF_TOKEN`, `TELEGRAM_TOKEN`, `DASHBOARD_API_KEY`, `BYBIT_*` остаются в открытом `.env`.
- В окружении аудита `SECRETS_MASTER_KEY` **присутствует** в списке переменных `.env` (значение не читалось), то есть локально шифрование, вероятно, включено. Для production это не гарантировано.
- **Что сделано правильно:** `.env` не отслеживается Git (`git check-ignore -v .env` → `.gitignore:2`); `bot/data/credential_vault.json` тоже (`.gitignore:21`); `website/.env*` (`website/.gitignore:34`). `git ls-files` не содержит ни одного файла секретов — совпадения по `passwords.py` / `credential_vault.py` являются исходным кодом, а не секретами.
- Сам файл vault получает `chmod 0o600` (`credential_vault.py:72`).
- Шифрование, когда включено: **AES-256-GCM**, случайный nonce на операцию (`secrets.token_bytes`), формат `nonce || ciphertext` (`encryption.py:65-68`).
**Файлы и маршруты:** `.env`, `bot/data/credential_vault.json`
**Текущее поведение:** Защита секретов опциональна и зависит от одной переменной окружения. Отсутствие ключа не является ошибкой запуска — система просто работает менее защищённо.
**Ожидаемое поведение:** В production отсутствие `SECRETS_MASTER_KEY` должно быть **фатальной ошибкой запуска**, а не тихой деградацией.
**Влияние на пользователя:** Компрометация хоста даёт брокерский токен в открытом виде. Мера смягчения: у токена нет прав на вывод средств ([S-08]).
**Влияние на бизнес:** Прямой риск для средств клиента.
**Техническое влияние:** `bot/security/config_validation.py` уже существует и проверяет связанные условия (например, `DASHBOARD_API_KEY` при bind на все интерфейсы, `:35-38`) — точка для добавления проверки есть.
**Корневая причина:** Осознанный выбор в пользу простоты локальной разработки, не сопровождённый строгостью в production.
**Сайт об этом говорит честно** (`faq.a6`): «Шифрование включается мастер-ключом — если он не задан при развёртывании, ключи останутся в обычном .env, и это нужно исправить до боевого запуска».
**Рекомендация:** Добавить в `config_validation.py`: при признаке production (например, `TINKOFF_SANDBOX=false` или явный `QF_ENV=production`) отсутствие `SECRETS_MASTER_KEY` → отказ старта с внятным сообщением. Хранить сам мастер-ключ вне `.env` (переменная окружения службы, Vault).
**Зависимости:** [S-05]
**Оценка объёма:** S
**Критерии приёмки:** При `TINKOFF_SANDBOX=false` без `SECRETS_MASTER_KEY` процесс не стартует и печатает причину; тест это фиксирует.
**Roadmap ID:** RM-P1-018

<a id="s-07"></a>
### [S-07] Сильные стороны безопасности (сохранить и не регрессировать)

**Статус:** VERIFIED — положительное наблюдение

**Проверено фактическими пробами** (Dashboard на 5051, без сессии):

| Категория | Результат |
|---|---|
| Данные (`/api/v2/health`, `environment`, `portfolio`, `positions`, `trades`, `equity`, `faults`, `settings/credentials`) | **401** |
| Legacy (`/api/platform/overview`, `signals`, `stream`, `/api/stats`, `/api/settings/tokens`) | **401** |
| Действия (`POST engine/start`, `engine/stop`, `learning/run-cycle`, `platform/engine/start`, `platform/signals/generate`) | **401** |
| Защищённая страница `/` | **302** → `/login` |
| Публичные намеренно: `/health` (тело `{"db":true,"status":"ok"}`), `/api/v2/auth/session` | 200 |

Ключевые решения:

1. **Fail-closed модель доступа** (`app_factory.py:236-275`): allow-list **путей**, а не IP, с прямым указанием, что прежняя инверсная модель оставляла открытым «любой роут, о котором никто не вспомнил». Список короткий и проверяемый глазами: `/health`, `/login`, `/api/v2/auth/session`, `/api/v2/auth/login`, `/api/internal/push` + префиксы `/static/`, `/miniapp`.
2. **CSRF дважды**: `@mutating` проверяет пер-роут, а `before_request` дополнительно ловит любой мутирующий роут, забывший декоратор («belt-and-braces» — прямо в комментарии).
3. **`/api/internal/push` защищён корректно** (`legacy_api.py:344-368`): общий токен через `hmac.compare_digest` (constant-time), fallback — только loopback, причём по **реальному TCP-peer** (`request.remote_addr`), с явным объяснением, что `X-Forwarded-For` подделывается клиентом. Это правильный разбор именно той ошибки, которую обычно допускают.
4. **CSP с nonce на Dashboard**, причём `frame-ancestors` **контекстный**: `https://web.telegram.org` для путей Mini App и `'none'` для остального (`http_middleware.py:110-112`) — точная настройка, а не глобальное послабление.
5. **`Cache-Control: no-store` на все `/api/`** — «аутентифицированная операционная поверхность не должна кешироваться общим прокси» (`:120-121`).
6. **HSTS** — `max-age=31536000; includeSubDomains` при `_HTTPS` (`:123-127`). На localhost отсутствует ожидаемо. **Требует проверки, что `QF_HTTPS=1` выставлен в production** ([OQ-OPS-04](14_OPEN_QUESTIONS_AND_DECISIONS.md)).
7. **Werkzeug debug отказывает при небезопасном bind** (`dashboard.py:47-53`) с формулировкой «консоль Werkzeug это удалённое выполнение кода».
8. **Маскирование секретов в аудите** (`guards.py:136-141`) — по подстроке `token|secret|password|api_key|apikey|credential|hash`.
9. **Email маскируется в логах сайта** (`beta/adapter.ts`): `a***@domain`, с обоснованием, что иначе лог хостинг-провайдера становится хранилищем PII с неизвестным сроком хранения.
10. **Rate limit на публичном эндпоинте сайта** (`api/beta/route.ts`): 5 req/min/IP, с честным перечислением ограничений (Map на процесс, `X-Forwarded-For` подделывается) — «это floor, не WAF».
11. **Honeypot отвечает как успех**, «чтобы бот ничего не узнал».
12. **Валидация всех query-параметров v2** с отказом вместо тихого fallback — предотвращает подмену среды (sandbox/live).
13. **Порты БД и Adminer привязаны к `127.0.0.1`** в `docker-compose.yml`, а не наружу.
14. **`drop_pending_updates=True`** у Telegram-бота — после простоя не отрабатывается лавина устаревших команд.

## 3. Веб-уязвимости: покрытие (VERIFIED / INFERRED)

| Класс | Состояние | Доказательство |
|---|---|---|
| **SQL injection** | Низкий риск | Репозитории на SQLAlchemy с параметризацией; `_db_rows` (`platform_routes.py`) использует `text()` с именованными параметрами; `arg_ticker()` ограничивает форму идентификатора вместо доверия LIKE-шаблону |
| **XSS (Dashboard)** | Низкий риск | CSP с nonce; `object-src 'none'`; SPA строит DOM через `el()`-хелперы, а не `innerHTML` из данных (INFERRED из `dom.js`) |
| **XSS (сайт)** | Не ограничен политикой | [S-02]; практический риск низкий — SSG, нет пользовательского контента |
| **CSRF** | Закрыт | Double-submit + `SameSite=Strict` + двойная проверка |
| **SSRF** | **Требует внимания** | `BETA_WEBHOOK_URL` (`website/src/lib/beta/adapter.ts`) — исходящий `fetch` на URL из переменной окружения. Не пользовательский ввод, поэтому не SSRF в строгом смысле, но конфигурационная ошибка направит запросы куда угодно. Риск низкий, контроль — процедурный |
| **Injection в Telegram** | Закрыт | Тикер: `isalpha()` + ≤12; количество: `int > 0`; **проверка подмены callback-данных** ([T-06](05_TELEGRAM_BOT_AUDIT.md)) |
| **Открытый редирект** | Требует проверки | `views.login?next=<path>` (`views.py:71-73`) — параметр `next` используется для возврата. **UNVERIFIED:** не установлено, валидируется ли он как относительный путь. Проверить перед production |
| **Clickjacking** | Закрыт | `X-Frame-Options: DENY` + `frame-ancestors` на обоих surface |
| **Rate limiting** | Частично | Dashboard: логины (2 уровня). Telegram: 30/60 с. Сайт: 5/мин на `/api/beta`. **Не покрыто:** общий rate limit на API Dashboard |
| **CORS** | Не настроен и не нужен | Оба surface — same-origin; `connect-src 'self'` в CSP Dashboard |
| **Webhook validation** | Не применимо / отсутствует | Входящих вебхуков нет (Telegram работает polling). Валидация `initData` Mini App **отсутствует** — [T-03] |
| **Dependency vulnerabilities** | 3 high (npm) | [S-03]. **Python-зависимости не проверены** — `pip-audit`/`safety` не установлены |
| **Supply-chain** | Частично | `package-lock.json` фиксирует версии. `requirements.txt` использует `>=` вместо `==` — сборка невоспроизводима, апстрим-компромисс попадёт при следующей установке. Это отдельное замечание ниже |
| **Логирование PII** | Хорошо | Email маскируется; секреты маскируются в аудите |

**Дополнительное замечание — невоспроизводимые Python-зависимости.** `requirements.txt` задаёт только нижние границы (`pandas>=2.0.0`, `flask>=3.1.0`, `cryptography>=42.0.0`, …). Две установки в разные дни дают разные версии; скомпрометированный или сломанный релиз попадает в сборку автоматически. Для финансового продукта нужен lock (`pip-compile` / `requirements.lock` / `uv.lock`). Объём: S. Roadmap: RM-P1-019.

**Низкий / не проверено:** penetration-тестирование, уязвимости Python-зависимостей, реальная production-конфигурация (TLS, прокši, права ОС), incident response и организационные права доступа. **Этот аудит не заменяет внешний security review перед работой с реальными деньгами клиентов.**
