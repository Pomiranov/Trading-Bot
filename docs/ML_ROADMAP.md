## 0. Философия (неизменная)

- Бот не переучивает математику — он меняет **доверие** к стратегиям статистикой.
- Правила (Швагер) заморожены как знания; ML оценивает решения, **не принимает их**.
- Любое изменение входит в прод только через **A/B-гейт**: победа над baseline на OOS.
  Проиграл — заморозка (прецеденты: гл.9 стопы, wrd_moex).
- Малые выборки = главный риск. Не подгонять параметры под один период.
- Один этап = одна сессия Claude Code (plan mode → build mode) → коммит.

## Этап 2 — supervised ML: LightGBM как эксперт-оценщик

**Идея:** ML оценивает качество сигнала до входа, решение остаётся за системой правил.

**Схема потоков (важно — не путать направление):**
```
сигнал от rules_engine
  → market_features (снимаются в момент сигнала)
  → LightGBM → P(успех)
  → check_signal (рядом с belief_system) → множитель размера / пропуск
  → risk_manager → сделка
  ...после закрытия:
  decision_evaluator → decision_quality → ОБУЧАЮЩАЯ МЕТКА для LightGBM
```
`decision_quality` — таргет для обучения, не потребитель предсказания.
Встраивание — в существующий `orchestrator.check_signal()`, перестройка не нужна.

**Гейт входа в прод:** стандартный A/B — стратегия с LightGBM-фильтром против
той же стратегии без фильтра, на OOS. Проиграл — заморозка.

**Гейт перехода к этапу 3:** этап 2 дал **устойчивый** OOS-выигрыш.
Если простая модель на наших фичах не работает — сложная не спасёт,
а лишь спрячет проблему за сложностью.

## Этап 2.5 — экспертная архитектура (Mixture of Experts)

Развитие check_signal в «комитет экспертов». Не отдельный этап, а постепенное
расширение этапов 2–3.

```
Рыночные данные → Rules Engine → Market Features
        ┌────────────┬────────────┬────────────┬────────────┐
        ▼            ▼            ▼            ▼
    LightGBM    Risk Expert   Regime Expert  News Analyzer
   (качество    (риск          (тренд/флэт/   (sentiment,
    сигнала)     системы)       волатильность)  макрориск)
        └────────────┴────────────┴────────────┘
                     │
          Decision Fusion Engine  (= check_signal)
                     │
        Belief System → Risk Manager → Исполнение
```

### Требование к наследованию доверия (найдено 27.07, долг №8)

**`confidence` наследуется производной стратегией ТОЛЬКО при совпадении набора
правил.** Производные строки `belief_system` создаются засевом из исходной
(`trend_moex_live` ← `trend_moex`, `osc_range_moex_d1_fwd` ← `osc_range_moex_d1`),
и раньше засев копировал `confidence` — то есть доверие, измеренное на ДРУГОМ
наборе правил. Так `osc_range_moex_d1_fwd` получил 0.6574 при нуле собственных
сделок, а `main.py` был заряжен скопировать 0.2887, которое не описывает ни EMA50,
ни то, что исполнится, и при этом проходит порог `MIN_STRATEGY_CONFIDENCE = 0.20`.

Совпадение набора проверяется по **отпечатку `rules_version`**
(`RulesEngine.rules_version`, штампуется в каждую строку `trades`).

**Отпечаток считается по ВСЕМУ разобранному yaml, а не по секциям
`rules`/`exit_rules`.** Исправлено 2026-07-28: исходная формулировка требования
называла эти две секции, и она была **дефектна по существу** — фикс A3
(EMA21 → EMA50) реализован как `data["indicators"]["ema_slow"] = 50`
(`run_ab_trend_fix.py:71`), то есть живёт в секции `indicators`. Хеш по
`rules`/`exit_rules` дал бы вариантам `baseline` и `a3_ema50` ОДИНАКОВЫЙ
отпечаток — слепое пятно ровно на том дефекте, ради которого требование и
вводилось. Перечисление секций и есть способ его завести.

Ограничение, известное и записанное: отпечаток покрывает только yaml. Смена
дефолта на стороне движка сравнимость нарушит, а отпечаток не сдвинет.

**Принципы:**
- Ни один эксперт не открывает/закрывает сделку единолично. Эксперты дают
  оценки, решение — за Fusion + Risk Manager.
- **Fusion — тоже модель, её тоже можно переобучить.** Начинается максимально
  тупой (произведение множителей, каждый в диапазоне ~0.5–1.5). Усложнение —
  только через A/B-гейт.
- **Принцип заменяемости экспертов (главный принцип архитектуры).**
  Эксперт — не постоянный житель системы, он постоянно доказывает полезность.
  Каждый эксперт обязан:
  - иметь feature flag (`enabled/disabled`) — включение и выключение одним флагом;
  - иметь собственные метрики качества (вклад в OOS-результат, не только «своя точность»);
  - проходить A/B + OOS перед включением;
  - регулярно переоцениваться (раз в N месяцев, симметрично гейту на вход);
  - **флагаться системой** при падении метрик — но отключается ЧЕЛОВЕК.

  *Почему не полная автоматика:* на D1 «перестал помогать» на окне 30–50 сделок —
  чаще шум, чем сигнал (тот же принцип, что confidence <20 сделок → 0.5).
  Плюс порог/окно автоотключения — сами параметры для оверфита.
  Движок считает и флагает, человек решает — как везде в системе.
  Исключение — авария: эксперт технически сломан (исключения, мусорные
  значения) → Fusion автоматически игнорирует его вывод и работает без него.

**Порядок подключения (по соотношению польза/затраты):**
1. **Risk Expert** — расширение существующего risk_manager, дешевле всех.
2. **LightGBM** — данные уже копятся (этап 2).
3. **Regime Expert** — автоматизация уже доказанного вручную фильтра
   (structural_downtrend_filter: OOS PF 1.16 → 1.67). Честная формулировка:
   детектор режима (тренд/флэт/волатильность), без «психологии толпы» —
   измеримые фичи, не красивые слова.
4. **News Analyzer** — последним. Требует: источник новостей по MOEX
   (таблицы `news` не существует — долг), sentiment на русском, и главное —
   **доказательство, что sentiment предсказывает что-то на D1**. До этого — не строить.

**Риск дублирования:** «психология» (паника/эйфория/накопление) под капотом —
в основном волатильность и объём, которые уже в market_features. Новый эксперт
обязан добавлять информацию, а не переупаковывать существующие фичи.

## Этап 3 — далёкий горизонт: deep ML

**Условия входа (все обязательны):**
- Минутные данные, тысячи торговых дней, множество инструментов.
- На порядки больше сделок в истории.
- Симулятор исполнения (отдельный крупный инженерный слой).
- Этап 2 доказал устойчивый OOS-выигрыш.

**Что тогда возможно:**
- Transformer Encoder + self-supervised пре-трейн, market embeddings.
- RL (PPO/SAC) — для управления позицией или исполнения ордеров.

**Ключевое решение:** Transformer/RL — не отдельная новая система, а
**заменитель одного эксперта** в существующей архитектуре (например, Regime
Expert). Меняем модуль — не всё. Вход/выход — те же гейты, что у всех.

**Почему не сейчас (зафиксировано, чтобы не пересматривать под настроение):**
- Данных на 2–3 порядка меньше нужного (D1 ≈ 10.5k строк на все тикеры).
- RL на одном историческом пути рынка = гарантированный оверфит.
- Пре-трейн улучшает представление, но не создаёт новых сэмплов.
- Дисциплинарный rule-based контур работает и корректно отбраковывает мусор —
  менять его на «большую сеть в маленьких данных» — регресс.

## Что взято из плана ChatGPT (остальное отклонено)

- Лог-доходности / нормализованная волатильность вместо сырой цены —
  проверить, что фичи уже так устроены.
- Walk-forward как формализация текущей OOS-практики.
- Идея режимов рынка — но через доказанные правила/Regime Expert,
  не через HDBSCAN-кластеризацию на малых данных.
