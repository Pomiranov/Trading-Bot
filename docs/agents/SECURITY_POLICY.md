# Security Policy — секреты и границы доступа для агентов

Обязательно для всех агентов. Общие правила — [`AGENTS.md §8`](../../AGENTS.md).

---

## 1. Файлы, которые агент никогда не открывает

Ни `cat`, ни `Read`, ни `grep` по содержимому, ни копирование, ни включение в diff:

| Путь | Что это |
|---|---|
| `.env`, `*.env.local`, `Password.env` | боевые токены и пароли проекта |
| `bot/data/credential_vault.json` (+ `.tmp`) | брокерские креды, AES-256 |
| `data/credential_vault.json` | то же |
| `data/user_prefs.json` | runtime-состояние пользователя |
| `~/.codex/auth.json` | ChatGPT OAuth владельца |
| `~/.claude/.credentials.json`, Keychain записи | Claude OAuth |
| Gemini OAuth / Vertex credentials | Google креды |
| `~/.openhands/secrets.json`, `~/.openhands/agent-canvas/*key*.txt` | хранилище секретов OpenHands |
| любой `*.pem`, `*.key`, `id_rsa*` | приватные ключи |

`.env.example` открывать **можно** — это шаблон без значений.

---

## 2. Что можно сообщать о credential

Разрешено:

- существует ли файл или запись;
- тип credential (OAuth token / API key / service account);
- путь хранения;
- права файла;
- приблизительную дату изменения;
- относится ли credential к текущему пользователю;
- прошла ли проверка подключения.

Запрещено: значение, префикс достаточной длины для восстановления, base64-фрагмент, полный вывод команды, содержащей значение.

---

## 3. Запрещённые способы обращения с секретами

- **Не передавать секрет аргументом команды** — он попадает в историю shell и в список процессов. Использовать переменную окружения или stdin.
- **Не вставлять токен в URL git-remote** (`https://<token>@github.com/...`). Remote остаётся чистым HTTPS; аутентификация — через credential helper или `GH_TOKEN` в окружении процесса.
- **Не выводить окружение контейнера целиком** (`docker inspect` без `--format`, `env`, `printenv`). Запрашивать только конкретные ненужные-для-секретов переменные.
- **Не записывать секрет в файл внутри репозитория** — ни в `.env`, ни в конфиг, ни в тест, ни в фикстуру.
- **Не помещать секрет в handoff, PR, коммит, лог, отчёт.**
- **Не отправлять секрет во внешний сервис** и не просить владельца прислать его в чат.

## 4. Где секреты живут на самом деле

| Секрет | Место хранения | Кто выдаёт |
|---|---|---|
| Claude Code OAuth (для ACP в контейнере) | OpenHands Secrets → `CLAUDE_CODE_OAUTH_TOKEN` | владелец, через UI Canvas |
| Codex auth (для ACP в контейнере) | OpenHands Secrets, file-secret слот `CODEX_AUTH_JSON` | владелец |
| Gemini credential | OpenHands Secrets | владелец |
| GitHub PAT для backend | OpenHands Secrets | владелец |
| GitHub логин хоста | `gh auth` (Keychain macOS) | владелец, через browser OAuth |
| Секреты проекта (`TELEGRAM_TOKEN`, `TINKOFF_TOKEN`, `DB_PASSWORD`, `SECRETS_MASTER_KEY`, …) | `.env` вне git + `credential_vault.json` | владелец |

Ни одно из этих мест не является репозиторием. **Credentials никогда не сохраняются в репозитории** — ни в открытом, ни в зашифрованном виде.

## 5. Границы доступа агента

Агенту доступно:

- свой worktree под `/Users/danila/OpenHands/worktrees/Quant/`;
- canonical repository — **на чтение** (для сравнения и создания worktree);
- `~/.openhands` — только сервису Canvas, не агенту как файловое дерево.

Агенту **не** доступно и монтировать запрещено:

- `/Users/danila/Documents/GitHub/Trading-Bot` (вторая копия репозитория);
- `/Users/danila` целиком;
- `~/.ssh`, `~/.aws`, `~/.config/gcloud`, Keychain;
- Docker socket;
- `~/Downloads` и `~/Documents` целиком.

## 6. Правила, связанные с боевой системой

- **`TINKOFF_SANDBOX=false` — реальные деньги.** Переключение только владельцем, явным решением. Агент не меняет это значение ни в `.env`, ни в коде, ни в тестах.
- **`python3 -m qf_platform.migrate` без `--check`** на боевой БД — только с бэкапом и согласованием.
- **Не запускать Telegram-бота**, если может работать другой экземпляр: Telegram допускает один polling-консьюмер на токен (`A-05`).
- **`npm audit fix --force` запрещён** — тянет мажорный апгрейд Next (`S-03`, `OQ-SEC-01`).
- Dashboard по умолчанию слушает `127.0.0.1:5001`. Не менять `DASHBOARD_HOST` на `0.0.0.0` без reverse proxy и аутентификации.

## 7. Публикация наружу

Первый push ветки и первый PR в рамках задачи — **действие, требующее разрешения владельца**, если Task Specification не содержит явного разрешения на публикацию.

Причина: push публикует содержимое во внешний сервис; отменить публикацию нельзя — данные могут остаться в кэшах и индексах даже после удаления ветки.

Перед первым push агент обязан убедиться, что в коммитах нет:

```bash
git diff --cached --name-only                      # ничего из §1
git log -p --all -- .env bot/data/credential_vault.json data/credential_vault.json | head -1
# пустой вывод = секретов в истории ветки нет
```

## 8. Если секрет всё-таки попал куда не должен

1. Немедленно остановиться и сообщить владельцу (OWNER CHECKPOINT).
2. **Не** пытаться «затереть» историю самостоятельно: `rebase`, `amend`, `filter-branch`, force push агентам запрещены.
3. Указать: какой тип секрета, куда попал (файл / коммит / лог / PR), был ли push наружу.
4. Считать секрет скомпрометированным — требуется ротация владельцем, а не удаление следа.

---

## 9. Что проверяет Control Center при приёмке

- в изменённых файлах нет путей из §1;
- в handoff и PR нет значений секретов;
- remote не содержит токена;
- нет коммитов с `.env`, vault-файлами, логами;
- не изменялись `TINKOFF_SANDBOX`, `DASHBOARD_HOST`, branch protection.
