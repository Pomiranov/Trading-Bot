### [Q-01] CI/CD отсутствует полностью

**Статус:** VERIFIED
**Критичность:** Critical
**Приоритет:** P0
**Компонент:** Инфраструктура разработки
**Доказательство:**
- `ls .github/workflows` → `No such file or directory`. Каталога `.github` в репозитории нет.
- Поиск любых workflow-конфигураций (`find . -maxdepth 3 -name '*.yml' -path '*workflow*'`) → пусто.
- Ни GitLab CI, ни Jenkins, ни pre-commit hooks (`.pre-commit-config.yaml` отсутствует).
- При этом в проекте **11 готовых к автоматизации команд** (см. раздел 1) — инфраструктура проверок есть, оркестрации нет.
**Файлы и маршруты:** отсутствуют
**Текущее поведение:** Все проверки выполняются вручную по решению разработчика. Практическое следствие видно прямо в этом аудите: **два гейта не проходят** ([Q-02], [Q-03]), и это оставалось незамеченным.
**Ожидаемое поведение:** На каждый push и PR: typecheck, lint, `check`, pytest, build, `npm audit`, dashboard-тесты и dashboard-токены.
**Влияние на пользователя:** Регрессии доходят до пользователя.
**Влияние на бизнес:** Для финансового продукта отсутствие автоматических гейтов — базовый пробел процесса. Также блокирует безопасный рефакторинг, которого проекту требуется много ([A-05], [A-06]).
**Техническое влияние:** Каждая проверка уже сведена к одной команде с корректным exit code — workflow пишется почти механически.
**Корневая причина:** Проект развивался как личный; процессная часть не строилась.
**Рекомендация:** Один workflow с двумя job'ами (node / python). Начать с **уже зелёных** гейтов, чтобы CI сразу был осмысленным, и отдельным шагом (`continue-on-error: true` вначале) добавить два падающих — затем починить и убрать поблажку. Для pytest завести `QF_TEST_USER`/`QF_TEST_PASSWORD` на тестовой БД, чтобы включить 72 пропущенных теста.
**Зависимости:** [Q-02], [Q-03], [Q-04]
**Оценка объёма:** M
**Критерии приёмки:** Workflow запускается на push/PR; красный CI блокирует merge; все 14 команд из раздела 1 выполняются автоматически.
**Roadmap ID:** RM-P0-003

### [Q-02] Гейт токенов Dashboard падает: подтверждённое расхождение с дизайн-системой сайта

**Статус:** VERIFIED
**Критичность:** Medium
**Приоритет:** P2
**Компонент:** `bot/ui/static/check-dashboard-tokens.mjs`, `bot/ui/static/css/tokens.css`, `website/src/styles/tokens/color.css`
**Доказательство (фактический вывод, exit code **1**):**

Значения подтверждены в исходниках:

- `website/src/styles/tokens/color.css:73` — `--color-paper: #e4e1da;`

Примечательно: комментарий в `tokens.css:155-156` объясняет, что `--qf-paper` — «единственное место, где может появиться `--qf-paper`: "вы торгуете реальными…"», то есть токен несёт смысловую нагрузку индикации live-режима. Расхождение оттенка означает, что сигнал «реальные деньги» выглядит в Dashboard иначе, чем на сайте.
**Файлы и маршруты:** обе дизайн-системы
**Текущее поведение:** Гейт существует, работает, обнаруживает реальное расхождение — и **не запускается автоматически** (у Dashboard нет `package.json`, в `npm run check` сайта он не входит). Поэтому дрейф сохраняется.
**Ожидаемое поведение:** Либо значения синхронизированы, либо расхождение осознанно зафиксировано в самом гейте как допустимое.
**Влияние на пользователя:** Незначительное визуально, но подрывает заявление сайта «Dashboard и Telegram читают одно состояние» на уровне единства бренда.
**Влияние на бизнес:** Малое. Ценность находки — в том, что она **доказывает** тезис о необходимости CI: проверка уже написана и уже красная.
**Техническое влияние:** Два набора токенов для одного бренда ([D-05](04_DASHBOARD_AUDIT.md)).
**Корневая причина:** Токены сайта менялись при редизайне; Dashboard не обновлён; гейт не автоматизирован.
**Рекомендация:** (1) Подключить `check-dashboard-tokens.mjs` в CI. (2) Привести два значения к сайту **после визуальной проверки** — `--qf-paper` участвует в индикации live-режима, поэтому менять оттенок вслепую нельзя. (3) Рассмотреть генерацию токенов Dashboard из источника сайта, чтобы дрейф стал невозможен.
**Зависимости:** [Q-01]
**Оценка объёма:** S
**Критерии приёмки:** `node check-dashboard-tokens.mjs` → exit 0; проверка в CI.

```

  Point at an existing install:
    QA_PLAYWRIGHT=/abs/path/to/node_modules/playwright npm run qa:landing

  Or install it here:
    npm i -D playwright && npx playwright install chromium webkit
```
`playwright` отсутствует в `devDependencies` (`website/package.json` проверен целиком). Скрипты `qa:landing` и `qa:landing:webkit` объявлены и не работают.

**Рекомендация:** `npm i -D playwright` + `npx playwright install chromium webkit`, затем включить оба скрипта в CI. Это закрывает и пробел по кросс-браузерности из [03](03_WEBSITE_AUDIT.md).
**Зависимости:** [Q-01]
**Оценка объёма:** S
**Критерии приёмки:** `npm run qa:landing` и `qa:landing:webkit` → exit 0; оба в CI.

### [Q-06] Мониторинга и алертинга нет; health-checks есть

**Статус:** VERIFIED
**Критичность:** High
**Приоритет:** P1
**Компонент:** Observability
**Доказательство:**

**Что есть:**
- `/health` (публичный) → `{"db":true,"status":"ok"}` — минимально и без утечек.
- `/api/v2/health` (аутентифицированный) — расширенный.
- `health_service`, `system_health_service`, `faults_service` в `qf_platform/services/`.
- **Latency-probe собственных запросов** (`app_factory.py:_register_latency_probe`): измеряет время каждого `/api/` и отдаёт в `health_service.latency` — «measure our own request latency so the health strip can report it».
- `X-Request-ID` / `X-Correlation-ID` в каждом ответе; экран `events` фильтруется по `correlation_id`.
- Структурное логирование с ротацией (`LOG_FILE`, `LOG_MAX_BYTES`, `LOG_BACKUP_COUNT`), `infra/logrotate`.
- Таблица `system_events`, экран событий, механизм faults с подтверждением.
- Сайт: Vercel Speed Insights + Analytics (production).

**Чего нет:**
- `grep -rniE "sentry|prometheus|opentelemetry|statsd|datadog|grafana"` по `bot/` и `website/src` → **0 совпадений**.
- Алертинга нет: ни email, ни PagerDuty. Единственный канал оповещения — Telegram-уведомления (`notify_api_error`, `notify_risk_limit`), то есть тот же канал, который может быть недоступен.
- Внешнего uptime-мониторинга нет.
- **Примечательно:** к окружению разработки подключены MCP-серверы Sentry и Grafana, то есть инструменты доступны, а интеграции в коде нет.
**Файлы и маршруты:** `/health`, `/api/v2/health`
**Текущее поведение:** Состояние видно, только если оператор смотрит в Dashboard или получает Telegram-сообщение. Падение процесса ночью останется незамеченным.
**Ожидаемое поведение:** Внешний uptime-мониторинг `/health`; агрегация ошибок; алерт по остановке торгового цикла и по недоступности брокера.
**Влияние на пользователя:** Торговля может стоять часами незаметно.
**Влияние на бизнес:** Для сервиса, управляющего деньгами, отсутствие алертинга — блокер production.
**Техническое влияние:** Точки интеграции готовы (health-сервисы, structured logs, correlation_id).
**Корневая причина:** Операционный контур не закрыт.
**Рекомендация:** Минимум для beta: (1) внешний uptime-монитор на `/health`; (2) Sentry для агрегации исключений (`sentry-sdk` с Flask-интеграцией — дешёвый шаг, MCP уже есть); (3) алерт «торговый цикл не отчитывался N минут» на основе `trading_engine.record_cycle()`.
**Зависимости:** [D-02](04_DASHBOARD_AUDIT.md)
**Оценка объёма:** M
**Критерии приёмки:** Падение процесса вызывает внешний алерт в ≤5 мин; необработанные исключения агрегируются.
**Roadmap ID:** RM-P1-022
