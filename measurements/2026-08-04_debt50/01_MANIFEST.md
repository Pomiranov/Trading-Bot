## 🚩 ПОСЫЛКА ЗАДАНИЯ ОПРОВЕРГНУТА ЗАМЕРОМ

В задании: «25 × 4.3 при хранении как числа с точкой даёт `107.49999999999999` →
107. Это ЕДИНСТВЕННЫЙ из 17 параметров на границе `.5`; остальные 16 далеко от неё и
правильны при любом способе». **Обе половины неверны на этой платформе:**

```
repr(25 * 4.3) = '107.5'      -> ровно 107.5, а не 107.4999999999999
round(25 * 4.3) = 108          -> банкирское округление даёт ВЕРНЫЙ ответ
int(25 * 4.3)   = 107          -> неверный
```

| способ | расхождений с пре-регистрацией |
|---|---|
| дробь + целые (принято) | **0** |
| float + `round` (банкирское) | **0** |
| float + `floor(x+0.5)` | **0** |
| float + `int` (усечение) | **8** |

Усечением ломаются **восемь**: `macd_fast`, `macd_slow`, `macd_signal`, `ema_fast`,
`pivot_strength`, `pivot_max_age`, `rsi9`, `stoch_smooth`. ⇒ `pivot_max_age` **не
особенный**, и опасен не float, а **усечение**.

**Дробь всё равно принята, но по другому доводу**, и он записан: результат не зависит
ни от платформы, ни от того, какой способ округления выберет следующий автор. `round`
в Python округляет половину **к чётному** (`round(106.5) == 106`), то есть даёт разным
окнам разные правила; сегодня ни одно из 17 в эту разницу не попадает — опираться на
это значило бы опираться на совпадение.

Класс дефекта уточнён: не «число, верное на бумаге и неверное в машине», а **«довод,
верный по существу и неверный в деталях»**. Вывод (хранить дробью) уцелел; обоснование
заменено на измеренное.
